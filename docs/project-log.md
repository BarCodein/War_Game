## 1. 项目概况

War of Dots 是一个基于 Vite、Phaser 3 和原生 JavaScript ES Modules 的浏览器单机实时战略游戏课程项目。项目从早期 Canvas 原型逐步迁移为分层架构，当前包含：

- Phaser 游戏运行时和教学战役
- 可独立运行的 headless 模拟层
- 单位选择、移动、攻击、编队路径和暂停/倍速控制
- 战斗、士气、补给、占领、迷雾与胜负系统
- 地图编辑器、地图校验、保存/载入、导入/导出和试玩闭环
- 登录、注册、主页、战役选择和项目介绍页面
- Vitest 单元测试、Playwright 端到端测试和 500 单位性能基线

当前仓库状态：

- 分支：`develop`，跟踪 `origin/develop`
- Git 工作区：干净
- 提交数：50 个
- 提交时间：2026-09-03 至 2026-09-11
- 主要贡献者：`woo` 26 个提交、`BarCodein` 17 个、`zhijianlee821-hash` 5 个、`lllayuuuu` 2 个
- 技术栈：Node.js >= 22.12、Vite 8、Phaser 3.90、Vitest 5、Playwright 1.62

### 3. 有什么经验教训

- **先拆分模拟与渲染，再扩展功能**：`simulation` 不依赖 Phaser 或 DOM，使战斗、士气、补给和胜负规则可以直接用 Vitest 验证，降低了后续调试成本。
- **固定时间步长是实时游戏稳定性的基础**：模拟不直接依赖浏览器帧率，暂停、倍速和掉帧补算更容易保持确定性。
- **统一命令接口减少重复逻辑**：玩家输入、脚本敌军和未来 AI 都通过 `commands.js` 下令，避免为不同控制来源重复编写移动和攻击逻辑。
- **数值配置必须集中管理**：将规则数值放在 `src/config/values.js`，再用 GDD 镜像测试检查文档同步，能减少调参时遗漏代码或文档的问题。
- **性能优化应尽早建立基线**：空间分区、纹理烘焙和 500 单位基准应在功能开发期间逐步加入，而不是等到最后才定位瓶颈。
- **文档和代码规则必须同步合并**：最近的合并留下了 GDD 和移动测试的冲突标记，说明“合并成功”不等于“规则已经统一”，文档冲突也会直接破坏测试和后续开发。
- **规则调整必须同步测试**：士气、伤害、撤退速度和地图网格的修改同时涉及配置、GDD、模拟代码和测试，单独修改其中一处会造成镜像测试或行为测试失败。
- **自动化测试不能替代真实浏览器验收**：Playwright 能覆盖主要流程，但 GPU 性能、Edge、不同分辨率布局和视觉反馈仍需要人工确认。
- **页面展示和核心玩法应保持边界**：团队介绍、故事和认证页面可以独立演进，避免把展示需求直接混入模拟层。

## 4. 当前代码结构与运行链路

项目的主要运行链路如下：

```text
HTML 页面
  -> src/entries/
  -> BootScene / GameScene
  -> input 生成统一命令
  -> World.issueCommands()
  -> 固定步长 simulation.tick()
  -> rendering / HUD 读取世界状态
```

### 入口与页面

- `src/entries/game.js`：创建 Phaser 游戏并注册游戏场景、基准场景。
- `src/entries/editor.js`：启动地图编辑器场景。
- `src/entries/home.js`：主页文案和登录态相关行为。
- `src/entries/battlechoose.js`：战役卡片、进度和战役跳转。
- `src/entries/login.js`、`src/auth.js`：登录、注册、会话和访问控制。
- 根目录 HTML 文件和 `members/` 页面：承担游戏入口、展示页和团队介绍功能。

### 模拟层

`src/simulation/` 是规则核心，并且不依赖 Phaser、DOM 或渲染层，可以在 Vitest 中 headless 运行。

- `world.js`：世界状态、实体管理、命令入口和 tick 编排。
- `loop.js`：固定 1/60 秒时间步长、速度倍率和掉帧补算上限。
- `entities.js`：单位与城市的数据结构和工厂。
- `commands.js`：`move`、`attackMove`、`attack`、`hold` 等统一命令。
- `movement.js`：寻路、路径队列、单位分离和撤退移动。
- `combat.js`：接触战、冷却、目标选择、伤害和地形修正。
- `morale.js`：士气修正、削弱、动摇、失控、溃逃和投降。
- `supply.js`：城市补给容量、补给分配和超限损耗。
- `capture.js`：城市占领、争夺冻结和进度衰减。
- `fog.js`：可见、已探索和最后已知位置。
- `victory.js`：胜负条件。
- `map.js`、`spatial.js`、`ai.js`：地图校验/迁移、空间分区和脚本敌军。

固定 tick 顺序为：

```text
movement -> combat -> morale -> supply -> capture -> fog -> victory
```

### 渲染、输入与编辑器

- `src/rendering/scenes/`：负责资源加载、游戏场景、编辑器场景和性能基准场景。
- `unitRenderer.js`、`terrainRenderer.js`、`fogRenderer.js`：负责单位、地形和迷雾绘制。
- `hud.js`：负责任务进度、事件日志、暂停/倍速、状态条和胜负结算。
- `src/input/selection.js`：单选、框选、Shift 增减选择和取消选择。
- `src/input/orders.js`：将右键和轨迹输入翻译为统一命令。
- `src/input/keyboard.js`：暂停、速度切换和快捷键。
- `src/editor/editorStore.js`：以纯数据方式管理地图编辑状态，并复用地图校验。

### 配置与文案

- `src/config/values.js`：规则、交互、教学和性能数值的唯一权威来源，并进行深度冻结。
- `src/i18n/zh-CN.js`：当前默认中文文案。
- `src/i18n/en.js`：英文文案预留，当前未形成完整语言切换流程。

## 5. 测试与验收状态

已实现的性能方向包括：

- 固定时间步长和最大补算 tick 数。
- 64 px 空间分区，避免全单位两两检测。
- 地形和迷雾纹理烘焙，减少每帧重复绘制。
- `#bench` 性能基准场景和 500 单位模拟测试。

### 当前验证结果

- `npm run build`：成功完成生产构建。
- 构建仍输出若干警告：成员页脚本缺少 `type="module"`、成员背景图片路径未在构建时解析，以及部分 bundle 超过 500 kB。
- `npm test -- --runInBand`：失败，原因是 Vitest 不支持 Jest 的 `--runInBand` 参数。
- `npm test`：当前仍失败，共报告 10 个失败测试。除 `tests/unit/movement.test.js` 因残留冲突标记无法解析外，配置/GDD 镜像、i18n、迷雾、战斗、士气和补给测试也存在断言失败，说明最近合并后的规则和实现尚未完全同步。

## 6. 当前风险与待处理事项

### 高优先级：提交合并冲突标记仍存在

`docs/gdd.md` 和 `tests/unit/movement.test.js` 中仍可见 `<<<<<<<`、`=======`、`>>>>>>>` 标记。这说明最近的远程合并虽然已经生成提交，但至少这两个文件仍需要人工确认并清理。尤其是 GDD 当前同时保留了两套互相冲突的规则：

- 逻辑网格为 20 px 或 10 px。
- 水域可通行或不可通行。
- 对应的移动、寻路和配置镜像也存在潜在不一致。

在冲突清理完成前，不应把 GDD 视为唯一的产品规则来源。

### 中优先级：验收闭环尚未完全完成

代码和自动化测试已经覆盖主要 MVP 流程，但真实 GPU、Edge、三浏览器和视觉人工检查仍未完成。阶段 6 更准确的状态应描述为“自动化基线已完成，跨浏览器最终验收待完成”。

### 中优先级：构建产物体积和资源路径

地图相关 bundle 体积较大，构建时出现超过 500 kB 的提示；成员页还存在静态脚本和图片路径警告。它们不阻断当前构建，但会影响部署稳定性、首屏加载和后续维护。

### 低优先级：产品内容仍以 MVP 为主

英文切换、完整战役、自主战略 AI、回放、在线功能、战斗中途存档等内容仍不在当前 MVP 范围内；故事页、团队页和战役选择页已加入，但核心可玩内容仍以单个教学战役为主。
