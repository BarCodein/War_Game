# War of Dots 开发流程

> 本文档定义从浏览器原型演进到 MVP 的完整开发流程，以 `REQUIREMENTS.md`（产品范围）与 `AGENTS.md`（工程规范）为准绳。核心原则：**先文档后代码、模拟与渲染分离、每个阶段有可验证的出口条件**。

## 总体原则

- 需求状态分为「已确认 / 暂定 / 待决定」，暂定或待决定内容不得直接视为最终实现标准（`REQUIREMENTS.md` §1）。
- 按照 `REQUIREMENTS.md` §9 的开发顺序：先确认术语与需求，再编写设计文档与验收标准，确认后方可实现 MVP。
- 模拟逻辑、渲染、输入、控制器分离；可调规则集中在配置模块；用户可见文本集中管理，中文优先（`AGENTS.md`）。
- 核心模拟采用固定时间步长，不依赖显示器刷新率；避免全单位两两检测；以 500 活动单位 / 60 FPS 为性能目标（`REQUIREMENTS.md` §5）。
- 测试与实现同步进行，不最后补：Vitest 覆盖确定性规则，Playwright 覆盖关键浏览器流程（`AGENTS.md`）。

## 对原型的处理策略

`game.js` 不推倒重写：

- 可移植：路线行进、接触战斗、迷雾/战线采样等逻辑，移植为纯 JS 模拟层代码，与 DOM/Canvas 彻底解耦。
- 可参考：现有军事风格 HUD 的视觉设计可延续到 Phaser 渲染层，文案迁移到 i18n 模块。
- 需重写：原型中「逻辑与 Canvas 渲染耦合」的部分，恰好借迁移完成解耦。

## 阶段 0：需求收敛与设计文档

解决 `REQUIREMENTS.md` §8 的「待确认事项」，产出设计文档。

1. 逐项解决待确认事项，给出带依据的默认值并标注「暂定」：
   - 士气公式、阈值、反馈方式以及投降或移除规则
   - 单位和地形参数、伤害公式、目标选择与碰撞规则
   - 城市自动生产或玩家配置生产，以及城市恢复规则
   - 占领速度、争夺判定和恢复速度
   - 森林视野阻挡与敌军最后已知位置的表现
   - 教学关卡内容、任务触发细节及完整可玩条件
2. 产出三份文档：
   - **GDD（游戏设计文档）** — 数值表、规则公式、UI 草图、教学关卡流程
   - **技术架构文档** — 模块划分、数据流、地图 JSON schema（带版本号）、命令接口设计
   - **可验证的 MVP 验收标准** — 细化为可勾选的 checklist（对应 `REQUIREMENTS.md` §6）

**出口条件**：§8 全部条目有结论；三份文档评审通过。

## 阶段 1：工程骨架（Vite + Phaser 迁移）

1. 建立目录结构：
   - `src/simulation/`、`src/rendering/`、`src/input/`、`src/controllers/`、`src/config/`、`src/i18n/`
   - `public/assets/`（静态资源）
   - `tests/unit/`、`tests/e2e/`
2. Phaser 启动骨架：Game 配置 + 场景划分（Boot → GameScene，后期加 EditorScene），固定时间步长驱动模拟。
3. 横切模块先行：
   - **config 模块**：所有可调数值集中于此，替代魔法数字
   - **i18n 模块**：用户文本集中管理，中文优先并预留英文
4. 跑通 `npm run dev / test / test:e2e / build` 四个命令 + 一个 Playwright 冒烟测试。

**出口条件**：空场景可运行；构建产物可静态部署；测试命令就位。

## 阶段 2：纯模拟层（不碰渲染，质量核心）

将原型逻辑移植为纯 JS 模拟，可在无渲染环境下独立运行：

1. 固定时间步长核心循环；数据流单向：输入 → 命令队列 → 模拟 tick。
2. 实体与规则：轻/重型单位、城市、补给（每城 5 容量、超限损耗）、士气（低士气削弱、归零溃逃/投降/移除）、占领进度、战斗结算（距离/间隔/伤害/地形修正）。
3. **统一命令接口**（Command pattern）：人类输入、脚本敌军、未来 AI 走同一接口（`REQUIREMENTS.md` §4.5 硬性要求）。
4. 空间分区（网格哈希）代替全单位两两检测，为 500 单位目标打底。
5. 地图模型：版本化 JSON + 结构校验 + 迁移机制；低分辨率逻辑网格表达通行性、寻路成本、视野阻挡（`REQUIREMENTS.md` §4.3）。
6. Vitest 覆盖：战斗结算、占领进度、补给损耗、士气、胜负判定、JSON 校验/迁移、固定步长确定性。

**出口条件**：模拟层可在无渲染环境下跑完整一局（headless 测试通过）；邻居查询性能基线达标。

## 阶段 3：Phaser 渲染 + 输入

1. 渲染层只读模拟状态：单位、地形（平原/森林/水域/桥梁）、三态战争迷雾（当前可见/已探索/从未探索）、控制线。
2. 输入层（左键单选、拖动框选、Shift 增减、右键移动/攻击）翻译为命令进队列，输入与战斗逻辑不耦合。
3. HUD 沿用原型视觉风格，文案全部走 i18n 模块。
4. 相机移动、暂停与游戏速度控制。

**出口条件**：Chrome/Firefox/Edge 在 1280×720 与 1920×1080 下手动操作流畅；Playwright 覆盖选择与指挥流程。

## 阶段 4：教学战役 + 脚本敌军

1. 脚本行为（驻守、定时增援、条件触发进攻、预设目标移动）全部通过统一命令接口实现。
2. 教学关卡：任务触发、提示、完整可玩闭环（选择 → 指挥 → 交战 → 占领 → 胜负）。
3. 对称实现胜负条件：占领全部敌方城市，或消灭全部敌军且敌方无可生产城市；失败条件对称。

**出口条件**：Playwright 可自动打完教学关并断言胜负分支。

## 阶段 5：地图编辑器

1. 新建地图（名称/尺寸）、地形绘制/擦除、城市/出生点/桥梁放置移动删除、城市初始阵营设置。
2. 可玩性校验（双方出生点、城市存在等基本条件）。
3. localStorage 保存/载入、文件 API 导入/导出、一键测试并安全返回。
4. **编辑器与运行时共享同一地图模型**（`REQUIREMENTS.md` §4.6 硬性要求）。

**出口条件**：创建 → 保存 → 载入 → 导入 → 导出 → 试玩全闭环有 Playwright 测试。

## 阶段 6：性能验收与收尾

1. 500 活动单位、60 FPS 的可测量性能基线测试。
   - 已做：地形/迷雾烘焙为纹理（消除每帧数千矩形的 Graphics 重放）；`#bench` 基准页实测模拟 tick 平均 4.06ms / p95 5.60ms（预算 8ms）✓。
   - 待团队：真实 GPU 的三浏览器上跑 `#bench` 确认 ≥60 FPS（本机软件渲染仅 7 FPS，不代表真实性能）。
2. 三浏览器 + 两分辨率回归；`git diff --check`；构建产物静态部署验证。
3. 对照阶段 0 的验收 checklist 逐项勾销，未达标项排期。

**出口条件**：MVP 验收标准（`REQUIREMENTS.md` §6）全部通过。

## 贯穿全程的工程纪律

- 每阶段开功能分支，Conventional Commit 聚焦提交（`CONTRIBUTING.md`）。
- 需求变化先改文档再改代码，明确标注「已确认 / 暂定 / 待决定」。
- 提交前检查：`npm test`、`npm run test:e2e`、`npm run build`、`git diff --check`。
- 涉及 UI/交互的改动，在三款浏览器、两种分辨率下手动验证。
- 即使是独立开发，也保持分支与提交纪律，便于回溯与交接。
