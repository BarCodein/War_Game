## ① 内容架构设计 · 1 分钟

**【讲词】**

技术栈是 Phaser 3 加原生 JavaScript。

整个项目最关键的设计是**单向数据流**：输入 → 命令 → 模拟 tick → 世界状态 → 渲染。玩家的操作只产生命令，命令进入**完全不依赖渲染的模拟层**，渲染层只读状态做绘制。

这样做有一个好处，渲染层可以替换，不会碰坏规则。

模拟层内部，每个 tick 的系统顺序是固定的：移动 → 战斗 → 士气 → 补给 → 占领 → 迷雾 → 胜负；步长固定 **1/60 秒**，每帧最多补算 5 个 tick。固定顺序加固定步长，保证同一份输入永远得到同一局结果。

## ② 项目文件夹结构 · 0.5 分钟

**【讲词】**

代码按架构分层放在 `src` 下：`simulation` 是引擎，七个系统在 `simulation/systems`；`rendering` 是 Phaser 渲染与场景；`input` 和 `controllers` 负责输入命令化、暂停与倍速；`config/values.js` 是**所有数值的唯一来源**，任何模块不许硬编码数值；`editor` 是地图编辑器；`i18n` 集中管理文案，中文优先。

资源方面，关卡与地图 JSON 在 `public/assets`，贴图音效在根目录 `assets`；测试在 `tests/unit` 与 `tests/e2e`；设计文档在 `docs`。

## ③ 关键算法与数据结构 · 3 分钟

**【讲词】**

这一节分四块：数据模型、空间与寻路、战斗与士气、数据驱动的关卡。

**第一，数据模型。** 世界里所有实体都是**纯数据对象**：单位、城市、占领点、世界本身都只是普通对象，没有类继承，状态可序列化。

**第二，空间与寻路。** 敌人检测如果两两比较是 O(n²)，500 单位会卡死，所以我们用**均匀网格**：格子边长 64 像素，每 tick 重建是 O(n)，每个单位查邻居是 O(1)；性能预算定在 500 单位下单 tick 不超过 **8 毫秒**，并用一个专门的性能测试守住它。寻路在 **10 像素逻辑网格**上跑 A*：四方向、森林代价更高、高山不可通行，结果缓存在模块级 `pathCache`。命令下达时一次规划整条路径，所以屏幕上的轨迹就是单位真正会走的路线。另外，地图外的目标点会被夹回地图矩形内，避免单位走进没有渲染的区域。

**第三，统一命令接口与战斗。** 人类和 AI 走**同一条通道**：`world.issueCommands`，模拟层不认识"玩家"和"电脑"的区别。移动和攻击前进都是"攻击前进"语义：沿路线行军，接触敌军就停下交战，敌军离开后继续走。战斗判定是"圆点接触"——距离小于等于半径和再放宽 2 像素才开打，保证画面显示接触才真的接触。伤害 = 基础伤害 × 士气倍率 × 防守方地形修正；血量低于 80% 后攻击力随血量线性下降，所以残血单位输出明显变弱。

**第四，士气、补给与迷雾。** 士气从 80 起步，每秒按环境修正：附近友军 +2、靠近城市 +5、补给充足 +1、断补 −2、持续交战 −8、行军 −5，进攻时消耗放大 1.3 倍；低于 60 削弱、30 动摇、0 就**溃逃**，溃逃单位不受指挥、速度降到 60%。每座城市补给容量 5 个单位，超编每秒掉 1 点血；城市 100 像素内每秒回 3 血、5 士气，所以守城有实际收益。迷雾是三态的——未探索、已探索、当前可见；森林中的敌军 60 像素内才可见，并保留"最后已知位置"标记。

**最后是数据驱动的关卡，这层我们花力气最多。** 一局游戏完整写在一个关卡 JSON 里：URL 上只带关卡 id，引擎读 `/assets/levels/<id>.json`，里面声明地图文件、初始兵力、增援波次、AI 行为和胜负条件——引擎里**没有任何一关的特例代码**。坐标引用统一成七种写法：绝对坐标、出生点、城市、占领点、命名锚点（各分按阵营或按 id）；编队落点统一是「锚点 + 每个单位的偏移 + 间距 × 序号」，所以整支部队换位置只要改一个锚点。校验分两层：关卡 JSON 的结构校验，和拿到地图之后的**引用交叉校验**——任何一处写错，游戏页顶部会直接弹出红色错误横幅并列出原因，不会静默用错数据跑。

**【提示】** 非讲词。第四块里的"补给"两句若超时可删（省 20 秒）；"七种写法"可简化为"绝对坐标、出生点、城市、占领点、命名锚点"。

## ⑤ 游戏机制与可玩性设计 · 2 分钟

**【讲词】**

我们的核心循环是：占领城市 → 城市提供补给与恢复 → 补给决定能养多大规模的部队 → 士气决定交战与撤退 → 最终以城市论胜负。

**城市是枢纽**：占领半径 60 像素，每个己方单位每秒贡献 5% 进度、叠加上限 15%，人离开后每秒衰减 3%；它提供 5 个单位的补给容量和回血回士气，所以打城市永远是收益最高的目标。

**地形是第二条博弈线**：道路加速 25% 且行军士气消耗减半，森林减速但防御提升，山地防御最强，高山完全不可通行。结果是**隘口、桥头、山口天然成为必争之地**——我们把宿北和塔山的主战场都放在山口和据点上。

**士气让战斗有了"击溃"而不只是"打死"**：断补、被多面夹击、持续交战都会让部队崩溃，崩溃后不受指挥、速度大减。所以玩家的操作空间不只是集火，还有断补、绕后、逼退。

**占领点是我们特意做的轻量目标**：只提供视野，不提供补给和士气，也不参与胜负。这样策划可以用它做前哨、观察哨，而不会意外改变经济与平衡。

**可玩性完全由数据决定**：教学关是蓝方 6 轻 2 重对红方 2 轻 2 重，敌人在 60 秒有一波增援；宿北战役只判定被标记的 5 个编队，AI 分三波增援并反冲击；塔山阻击战要守 8 个据点 300 秒，敌军分波次进攻、还会从侧翼登陆。

**平衡验证也很工程化**：我们写了一个"朴素玩家"脚本——每 5 秒全军攻击前进——在 headless 下跑完整局，测出胜负和用时，再回头改关卡 JSON 的兵力配比。因为城市不再自动生产单位，兵力完全由关卡设计决定，"拖时间涨兵"是没用的。

**【提示】** 非讲词。三关举例若超时只讲宿北（省 20 秒）。

## ⑥ 效果演示 · 2.5 分钟

**【准备（非讲词）】** 提前 `npm run dev`，浏览器开三个标签页：`/index.html`、`/game.html?level=fracture-canyon`、`/editor.html`。现场异常时改用已构建的 `dist/`（`npm run preview`）或直接放录屏。

**【讲词 + 操作】**

演示分五步。

**第一，首页与战役选择。**（点开首页）首页有游戏和编辑器两个入口。（进战役选择页）这三张关卡卡来自关卡索引文件，和游戏内读的是同一份数据。

**第二，教学关实战。**（进断裂峡谷）左上角是我的编队，左下有城市状态——占领进度和补给占用，右侧是任务进度和战场通讯。我先框选全部单位，从已选单位拖出一条轨迹、再右键确认，可以看到路径是绕开地形规划出的真实路线。（推进到交火）右侧日志会滚动汇报接触与占领。（占领信标）占下敌方信标后弹出结算界面。

**第三，宿北战役。**（切到 `?level=subei_battle`）这一关换的是胜利条件：不占城，而是**歼灭被标记的 5 个红军编队**，AI 会分三波增援并反冲击。我把倍速调到 ×2 演示一次接触与溃逃。

**第四，塔山阻击战。**（切到 `?level=tashan_battle`）这是防守关：守住 8 个占领点到 300 秒，敌军从北面分波次进攻。请注意——**同一个引擎、完全不同的关卡规则，只换了一个 JSON**。

**第五，地图编辑器。**（切到 `/editor.html`）我画一格森林、放一个占领点、切换地图尺寸，然后点"试玩"直接进游戏，再点"返回编辑器"回到刚才的编辑状态。

最后（打开 `/game.html#bench`）是性能基准页：500 个活动单位的模拟 tick 平均耗时在 **8 毫秒**预算内。

一句话收尾：引擎不含任何关卡特例，新关卡就是写一份 JSON——这也是我们下一步要做的：按同样的格式把更多战役加进来。

**【提示】** 非讲词。塔山那一关不要玩到 300 秒结算，展示据点与时限即可；若时间紧，第三、四步各压成一句话（省 40 秒）。

## 附二：Q&A 预案（非讲词）

1. **为什么不用 TypeScript / 前端框架？** 课程约束是原生 JS；我们把类型安全换成了"纯数据 + 校验函数 + 138 个用例"，换来的是可 headless 测试。
2. **为什么城市不生产单位？** 让兵力完全由关卡设计决定，避免拖时间自动涨兵破坏配比；逻辑仍保留在 `supply.js`，一个开关即可恢复。
3. **怎么保证确定性？** 固定 1/60 步长、固定系统顺序、模拟层无随机数、空间网格按桶序遍历。
4. **性能怎么测的？** 单元测试里 500 单位断言平均 tick ≤ 8 ms，另有 `#bench` 页面现场测帧率。
5. **AI 是什么水平？** 目前是数据驱动的脚本 AI：定时增援、条件触发、攻击最近敌军；因为它和玩家共用命令接口，后续换更强的 AI 不需要动引擎。
